# Voics mobile (Expo, React Native)

iOS first, Android from the same code ([client#203](https://github.com/discordy-voics/client/issues/203), plan: docs `plans/2026-11-03-mobile-app.md`, stack: ADR 0024). The app signs in (with two-factor), keeps a gateway connection that resumes when the app returns to the foreground, and lists your servers and their channels of every kind the desktop sidebar shows (text, announcement, voice, stage, forum). Tapping a text channel opens its messages (read, send, reply, edit, delete, reactions). There is no tab bar: the main screen follows the desktop client, a narrow server rail on the left (Direct messages on top, a separator, then servers and folders with the same selected pill, unread pip and mention badge) beside a column with the selected server's name and channels by category (or the DM list), and a user panel at its foot. Tapping a channel or conversation opens the chat full screen over the rail; the back arrow, the iOS edge swipe and the Android back button return to it. The bell in the column header opens Notifications and the user panel (name or gear) opens Settings. The DM column lists your 1:1 and group conversations (newest first) and opens them in the same message screen; encrypted conversations show the private-delivery notice. The chat header follows desktop: back chevron only (no route name) on every pushed screen, then `# channel` in a server, or the friend's avatar and name in a 1:1 DM with voice call, video call and profile buttons (in Expo Go the call buttons show a "not in this test version" notice); the server members button sits in the right-hand slot (see Servers below). Messages show avatars, role-coloured names and times with consecutive messages grouped, markdown text, system messages (join, pin, call, group changes), the edited marker and the message being replied to above the reply; long-pressing a message opens a bottom sheet with react, reply, Copy Text, Select Text (a sheet with natively selectable text), edit and delete. The composer is a tall rounded field that grows with the text, with a + button (photo library, camera, files; previews with remove, 25 MB and 10 files per message) whose buttons centre on a single-line input, and an emoji button that opens the picker and inserts at the cursor. Long-pressing a message also offers Copy Message Link, Mark Unread and (with Manage Messages) Pin; the + chip under a message and More reactions open the same picker, and long-pressing a reaction lists who reacted. Dragging a message left 64 pt replies with a haptic tick. The header's ... button opens a menu with Mark as read, Mute (durations) or Unmute, Notification settings (server default, all, mentions, nothing) and Invite people, a send button that appears with text, and a `Message #general` / `Message @bob` hint; it rides the keyboard frame by frame (see Motion and design below). Opening a chat acks the latest message so its unread dot clears, like desktop. Tapping an author, or the profile button in a 1:1 DM, opens their profile (avatar, names, About me, Friends since). Attachments show as an image and video grid (up to four tiles, then +N, spoilers blurred until tapped) with a full-screen viewer (swipe, pinch to zoom), audio and file rows, and unsent messages show upload progress with Cancel; they upload through the core presigned-slot flow with an XMLHttpRequest progress adapter (`src/adapters/xhrUpload.ts`). Opening a chat shows a New divider above the first unread message and a count bar with Mark as read, scrolls to it, and a Jump to latest button appears after scrolling away. Root QA on the existing Android emulator has verified login, message delivery, foreground/background presence and a native voice connection. The iOS simulator workflow verifies native startup and form navigation; signed-device push and physical-iPhone media still need acceptance.

**Servers (client#274).** Voice and stage channels sit in their categories with the speaker icon, the user limit and the people connected right now (avatar, name, muted, deafened, camera and live marks, from voice state). Tapping one opens a screen with the channel and its people. In Expo Go it says "Voice isn't in this test version yet"; in a development build it has a Join voice button (see Voice and calls below). Ephemeral and peer-to-peer channels show the lock (or link) icon and open on a plain message; forum channels open on their posts (see Forums below). The people icon in a server channel's header opens the member list (slides in from the right; grouped by hoisted role, then online and offline; avatars with status dot, role colour, owner crown, activity line, search, collapsible groups); tapping a person opens their profile sheet (roles, member since, About me) with a Message button that opens the DM. Tapping the server name opens the server menu: Invite people (expiry and use limit, then copy or share the link), Server settings (only with Manage Server, Manage Roles or Manage Channels) and Leave server (after a confirmation; not for the owner). Server settings has Overview (name, icon from the photo library), Roles (list with member counts and hierarchy locks; per role name, colour, display options and every permission, with the same locks the desktop applies), Members (search; kick and ban only for people you outrank, after a confirmation), Invites (create, copy, revoke) and Channels (create channel or category, rename, delete after a confirmation). Every page checks the same permissions as desktop and shows a note instead of controls when a deep link or a role change leaves the user without access. Not built from desktop's server settings: Emoji, Template, Discovery, Bans (the list and unban), Audit log, server banner and invite splash, description, voice region, system messages, inactive channel, default notifications, prune members, role reordering, duplicating a role, role icons, adding roles to members and members-with-a-role, per-member timeout, nickname, mod view, channel permission overwrites, topic, slowmode, age restriction and reordering of channels, pinned channels, the right-edge swipe that would open the member list, and Delete server. Attachments are next (client#206 follow-ups). Root QA on the existing Android emulator has verified login, message delivery, foreground/background presence and a native voice connection. The iOS simulator workflow verifies native startup and form navigation; signed-device push and physical-iPhone media still need acceptance.

**Notifications and direct messages (client#278, wave 2).** The bell opens the mentions inbox (`src/notifications`): the same entries as desktop's Mentions (core `mentionInboxStore`, filled by the dispatch router), grouped by server, newest first; tapping one calls `openMessage`, which asks the chat for a jump (`useReadNavStore.requestJump`) and pushes the chat route. The chat serves the jump in `useJumpToMessage`: it scrolls to the message when it is loaded, otherwise `MessageService.loadAround` fetches the window around it, the list then holds a window detached from the present (`hasMoreAfter`), `onStartReached` extends it with `loadNewer`, nothing is acknowledged while detached, and Jump to latest reloads the newest page. Reply previews, and later pins and search hits, use the same path. Mark read removes the entry (it does not ack the channel); Mark all read clears the list. `InAppBanner` (mounted in the root layout) shows a banner for `offerBanner(message)`, which the runtime calls for every incoming message; core's `incomingAlert` decides (own and silent messages, the chat on screen from the route (`channelIdFromPath`), mute, level, @everyone and role settings, Do Not Disturb) and the app must be in the foreground. The DM column adds Friends and New message rows, pinned conversations (`pinned_dm_channel_ids`, at most five, synced through user settings) and a long-press menu built from core's `buildDmMenu` (`src/dms/DmMenu.tsx`). `dms/new` is the New message picker (core `dmCandidates`; one person opens the DM, several create a group DM) and `friends` is the Friends page (core `friendsModel`: Online, All, Pending, Blocked, Add friend with `friendRequestError`). Group settings (name, icon, members) are not on mobile yet. Root QA on the existing Android emulator has verified login, message delivery, foreground/background presence and a native voice connection. The iOS simulator workflow verifies native startup and form navigation; signed-device push and physical-iPhone media still need acceptance.

**Find and navigate (client#278, wave 2).** Tapping the chat title opens `ChannelDetails` (a bottom sheet: name, topic, Search, Pinned messages, Threads in a server text channel, Members, Copy link; a 1:1 DM opens the profile instead, a group lists its people). `pins/[channelId]` is the Pins panel (`api.pins`, reloaded when `last_pin_timestamp` changes; Jump sets a jump request and goes back to the chat, Unpin needs Manage Messages in a server); the pin notice's link and details open it. `ProfileSheet` is the full profile: banner from `accent_color`, status dot and activity, `profileActions` (Message, Add friend, Accept, Remove friend, Request sent, Block with confirmation, Unblock), the note (core `saveUserNote`, saved on blur, restored on failure) and, from `userProfile`, mutual servers and friends; a sheet with a field lifts with the keyboard frame (`useReanimatedKeyboardAnimation`). Threads: core `threads` (naming, lookup, listing, locked rule); Create Thread in the message menu needs Create Public Threads in a channel that is not a thread (`NewThreadSheet` then `api.createThread`); a thread is a guild channel of type 10 to 12, opened through the same chat route with the parent channel's overwrites and Send Messages in Threads; `threads/[channelId]` lists the threads the client has (GUILD_CREATE and THREAD_CREATE), because the server has no list route yet (api#34). Search (`search/[channelId]`): core `SearchService.page` with `searchCandidates`, the query language and suggestions of `messageSearch`; Media runs `has:image` and `has:video` and merges, Files and Links run `has:file` and `has:link` (the Files tab drops images and videos, Links extracts the URLs from the text), results load a page at a time; chats with private delivery cannot be searched on mobile. Join a server: the + at the end of the rail opens `JoinServerSheet` (core `parseInviteCode`, `api.invite` for the preview, `api.acceptInvite`; a server you are in just opens). Voice channels have Open text chat, which opens the chat route with `chat=1`. Forum posts, group settings and rail reordering came in wave 3; report has no api yet.

**Settings and account (client#279, wave 3).** The user panel opens `settings` (`src/settings`): a search field over every page and row (core `settingsSearch`, the ranking desktop's settings search uses too; a result opens the page with the row marked) and the pages grouped as on desktop, then Log out (asks first, with desktop's wording). Pages: My account (username, email and password changes, two-factor setup, removal and backup codes, disable and delete, all behind the same password and typed-username steps as desktop; the email-verification banner; the authenticator key is shown to type in and an Open authenticator app button follows the `otpauth` link, because there is no QR drawing library in Expo Go), Profile (avatar and banner from the photo library, display name, About me, colour, status and custom status with expiry; sends only changed fields), Privacy and delivery (the default mode, with the encrypted modes switched off and explained because the encryption core is not in the app yet, per-chat overrides with Clear, and Blocked users with Unblock), Devices and sessions (core `authSessions`, Log out per device and for all others after a confirmation, the encrypted-message devices), Appearance, Accessibility, Notifications and Chat. Only settings the phone app honours are listed: desktop's Voice and video, Keybinds, Connection, Desktop, Advanced, Developer and About are desktop-only, and desktop has no Language page. Theme (Dark, OLED, Light), accent and Match iPhone appearance use `appearance/palettes.ts` (desktop's tokens converted to sRGB): styles read `theme` once when their module loads, so `appearance/boot.ts` (imported by the root layout right after `install`) rewrites the shared `theme` object from the stored preferences, and a new choice shows from the next start of the app (the page says so). Text size scales message text; reduce motion (also from the iPhone), role colours (in the name, as a dot, hidden), always-underline links, Display images and videos, spoiler display, reactions and emoticon conversion take effect at once. `PrefsSync` runs on mobile as on desktop, so theme, accent, text size, reduce motion, role colours, link underline and only-mentions follow the account. Report and block: Block User is in the message menu (not for yourself, bots or people already blocked) next to the profile sheet and the Friends tab, always after a confirmation; there is no report endpoint in the api (the moderation spec lists `POST /channels/{id}/messages/{id}/report` as not built), so the app has no Report control rather than one that cannot work. Not built in this wave: QR login (gateway#17). Root QA on the existing Android emulator has verified login, message delivery, foreground/background presence and a native voice connection. The iOS simulator workflow verifies native startup and form navigation; signed-device push and physical-iPhone media still need acceptance.

**Server administration (client#279, wave 3).** Server settings now has Emoji (upload from the photo library with the 256 KB bound, rename, delete after a question; Manage Expressions), Bans (list with reasons, search over name, id and reason through core `filterBans`, Unban after a question; Ban Members) and Audit log (core `AUDIT_ACTIONS` and `AUDIT_FILTERS`, filter by action and moderator, Load older entries with `before`; View Audit Log), each gated by `settingsPages` like desktop's tabs. Like desktop, the server menu only offers Server settings with Manage Server, Manage Roles or Manage Channels, so a member who holds only Ban Members, View Audit Log or Manage Expressions cannot reach those pages from the menu. The Members page opens `MemberActionSheet` for a member (also from the Manage member button of the profile sheet in a server): Roles (switches for roles below your highest, `assignableRoles`), Change nickname or Edit server profile for yourself (Manage Nicknames or Change Nickname), Timeout with desktop's presets and Remove timeout, Kick and Ban with the message-history window and a reason; every entry comes from core `memberCapabilities` (same hierarchy rules as desktop) and the page has a Timed out only filter. Roles has a Reorder mode with up and down buttons built on core `reorderPositions` (roles at or above yours never move) and `reorderRoles`. Channels has Reorder (core `channelOrder` step functions, one bulk `reorderChannels`, reverted when refused, with desktop's offer to sync permissions after moving into another category) and a page per channel: name, topic, slowmode, age restriction, voice user limit and bitrate, Delete channel after a question, and Permissions with allow, inherit or deny per permission for roles and members (`putOverwrite` and `deleteOverwrite` for what changed). The server menu adds Mark as read, Mute server (durations) or Unmute, Notification settings (level, suppress @everyone and role mentions, hide muted channels, via core `notificationActions`) and, for the owner, Delete server, which asks for the server name to be typed first (desktop asks a plain question). Marking read, saving the rail, leaving and deleting a server, and sending channel moves moved into core (`guildCommands`, `channelOrderCommands`) and desktop uses them. Not built: Template and Discovery pages, server banner and splash, description, voice region, system messages, inactive channel, default notifications, prune, duplicating roles, role icons, members-with-a-role, Mod View, drag handles (reordering uses buttons).

**Servers, discovery and groups (client#279, wave 3).** The + at the end of the rail opens Add a server: Create my own server (`CreateServerSheet`: empty or a built-in template from `builtinGuildTemplates`, or a pasted template link previewed with `guildTemplate`, then a name of at least two characters; the new server opens), Join a server (as before) and Discover servers (`discover`: public servers that opted in, searched after a short pause, narrowed by category or tag, Load more, Join or Open; the same `discoveryGuilds` calls as desktop). Long-pressing a server or folder in the rail opens `RailMenu` instead of dragging: Move up and down (inside a folder, or among the entries), Add to folder, Make a folder with another server, Remove from folder, and for a folder Rename or colour, Move and Ungroup, built on core `railLayout` through `railEditModel` and saved with core `saveRail` (shown at once, reverted if the save fails). Group DMs have a Group settings row in the chat details (`groups/[channelId]`): name, icon from the photo library, members (any member adds friends, only the owner removes people after a question, 25 at most) and Leave group; in an encrypted group the member controls are hidden with a note because changing who is in it needs a membership commit from the encryption core, which the mobile app does not have. A message with an invite link to this instance shows an invite card (server, who is in it, Join or Joined; lookups cached per code, dead links shown as invalid), and tapping such a link, or a `voics://invite/` link, opens the join sheet in the app (`InviteLinkSheet` in the root layout) instead of the browser. The deep link from outside the app needs the native build. Search has a Sort row (Newest, Oldest, Most relevant; core `SEARCH_SORTS`), which searches again from the start. Not built from this part of the plan: drag handles for reordering, server banner and splash.

**Forums, forwarding, drafts and the offline cache (client#279, wave 3).** A forum channel with server-stored delivery opens `ForumScreen`: its posts (public threads under it, active first and newest first, with their message counts), and New post (a title and a first message, sent as `createThread` with a `message`, as desktop sends it) only for someone who passes the same Create Public Threads check as starting a thread; opening a post shows it as a chat. Forward is in the message menu for messages stored on the server (not system messages, unsent ones or messages of private chats); `ForwardSheet` lists recent DMs and groups, then channels you may send in (core `forwardTargets` and `permissionsInChannel`), with an optional comment, and sends through core `forwardMessage`; private chats and encrypted server channels are shown disabled so nothing encrypted is ever forwarded in the clear. A forwarded message shows a Forwarded block with the copied text and files. Drafts: the composer keeps unsent text per chat in core `useDraftStore` after a short pause and when you leave the chat, restores it when the chat opens and clears it on send; chats with private delivery keep nothing. The offline cache (`src/offline/messageCache.ts`, in the installed device key-value store) saves the newest 50 sent messages of up to 30 server-stored chats when a chat loads and when it is left; opening a chat shows the saved messages at once and replaces them with the fresh page, and when the server cannot be reached they stay with a note. It is emptied when the session ends, never holds unsent or failed messages, and never holds private chats. Not cached: attachments' files and avatars, which expo-image caches on its own, and read state.

**Parity polish (client#280, wave 4).** *Quick switcher:* the magnifier in the column header opens `QuickSwitcher` (`src/switcher`), a tall `BottomSheet` with a search field over every channel, conversation, server and a few screens (Friends, New message, Notifications, Discover, User settings). It ranks with core `quickSwitcher` (prefix `@` people, `#` text, `!` voice, `*` servers and `*server channel`; with nothing typed, chats with mentions come first, then unread ones, then recently visited ones) and builds its channel rows with core `channelSwitcherItem`, which desktop's palette now uses too. Return opens the first result. *Slash commands and components:* typing `/` in a standard chat where you have Use Application Commands lists the matching commands (`useSlashCommands` loads them through core `InteractionService`, now `runtime.interactions`); choosing one opens `CommandSheet` with a control per option (choices as chips, booleans as a switch, numbers and text with core validation, people, roles, channels and mentionables from a list inside the same sheet through core `entityChoices`), then Run sends the interaction and an "app is thinking" row waits at the newest end until the bot answers. Buttons, string selects (single, or multiple with Apply within the min and max values) and user, role, mentionable and channel selects that bots attach to messages render under the message (`MessageComponents`; link buttons open the in-app browser for http and https only), and a form a bot opens (`INTERACTION_MODAL_CREATE`) appears as `InteractionModal` at the root. File options are not supported yet. Stickers are not built: desktop has only the Animate stickers setting and no sticker sending or display. *Tablet layout:* `ios.supportsTablet` is on, and when the shorter side of the window is 600 pt or more (`src/shell/layoutModel`; an iPhone in landscape stays a phone) `WideShell` keeps the rail and a 288 pt channel column on the left and shows every stack screen to their right: a chat, the member list, pins, settings. Channels and conversations replace the chat in the pane (`openChat`) instead of piling up, a server in the rail opens the channel you were last in, and with nothing open the pane asks you to pick one. The app stays in portrait (`orientation` is unchanged) and `requireFullScreen` is set, which Apple requires of an iPad app that does not rotate or take part in Split View. *User panel:* the avatar carries the presence dot (the status the gateway reports, so automatic Idle shows; hollow while Invisible); the name opens `StatusSheet` with the four statuses (the chosen one ticked), the custom status editor (text and when it clears, also on the Profile page through `CustomStatusForm`), Edit profile and Settings, and the gear still opens settings. *Categories:* a collapsed category keeps what has activity listed, as desktop does (core `visibleChannelIds`): the open channel, mentions, unread text channels and voice channels with people in them. *Theme and accent:* they are read once when the app starts (styles are built at load), so the Appearance page says on the Theme and Accent rows that a change takes effect after a restart, and says so again after you change one. *Not built, needs an owner decision:* polls and voice messages are new on both clients (see `docs/handbook/13-mobile-client.md`).

- Expo SDK 58, React Native 0.88, React 19.3, TypeScript strict. All versions are pinned; check them with `npx expo install --check`.
- `app.config.ts` reads the display name, URL scheme (`voics://`) and bundle id/package from `../desktop/brand.json` (`displayName`, `protocolScheme`, `appId`). The icon is `../desktop/build/icon.png`. The bundle id and Android package are `nl.voics.app`.
- The workspace uses pnpm with `node-linker=hoisted` (root `.npmrc`), which Expo supports; Metro picks up the monorepo automatically. Desktop and mobile pin the same React version so there is one copy.

## Voice and calls (development build only)

Joining voice needs a development or preview build: @livekit/react-native-webrtc (WebRTC, with its frame cryptor) and react-native-incall-manager (speaker or earpiece) are native, and `src/voice/nativeVoice.ts` loads them only when `isNativeBuild` is true, so Expo Go still starts and shows the "not in this test version" notices. Implemented behavior and remaining device checks:

- Join and leave a voice channel (tap it, then Join voice), mute, deafen, who is here, a green ring on whoever speaks, and a bar above the user panel while connected (mute, leave, tap to return). Speaker or earpiece switch on the call screen.
- DM calls: the voice button in a DM opens the call screen and joins (the server rings the others). An incoming call shows Accept and Decline over any screen while the app is open (`CALL_DECLINE` for decline). With CallKit (below) the ring is the system call screen, also while the app is closed.
- End-to-end encrypted calls (Ephemeral and P2P DMs, accounts with `e2ee_calls_default`, and any call where someone has it on) work like on desktop: the DAVE session runs on the Rust engine (`VoicsCrypto`), frames are protected by the native frame cryptor (`mobileFrameCryptor.ts`), the call header shows "end-to-end encrypted" once keys are active, and the Privacy page has the "Encrypt all my calls" switch. Nothing is sent or played in clear: the cryptor is attached and confirmed enabled before the answer is applied, a track reaches a sender only after that, remote tracks stay muted until their receiver is protected, and a call that announces another protocol version than 2, or H.264 video, or a phone without the crypto module is refused with a clear message. Needs a new development build (the WebRTC package changed to `@livekit/react-native-webrtc` 150.1.0). Not run on a device yet.
- Video calls (client#299, development build): the camera button on the call screen turns your camera on and off (front camera first, 720p at 30 frames a second, the shared VP8 default on desktop and mobile, including encrypted calls), the flip button releases the old capture and opens the requested camera through the same protected sender; the facing indicator changes only after success, and the video button in a DM header joins the call and turns the camera on once it is connected. The call screen follows desktop's stage (core `domain/stageLayout`, `src/voice/stageModel.ts`): one to one is the other person large with your own small tile in the corner, a group is a two-column grid, and tapping a tile enlarges it with the others in a strip (tap again to go back). Without any video it stays the plain participant list. Someone's screen share is a tile with a Watch button (core `watchStream`) until you opt in. Your own front camera is mirrored. Camera permission: the iOS prompt appears on first use; when access is off the app says so and offers Open Settings. The camera is turned off when the app goes to the background (iOS stops capturing there), not for a permission prompt. Security: the camera track reaches the peer connection only through `VoiceSession.setCameraTrack`, which in an encrypted call pauses the sender, sets the track, attaches and enables the frame cryptor and only then resumes it (`mobileCallController.ts`); flipping the camera does not replace the sender, and after a reconnect the camera is put back through the same path (core now clears the camera and screen track when a peer connection is closed, because their senders are gone). Not run on a device yet.
- Background calling (client#298, development and store builds on iPhone). Audio survives locking the phone and leaving the app (`UIBackgroundModes`: `audio`). DM and group calls appear in the system call UI through CallKit and ring on the lock screen, also when the app is closed, through a PushKit VoIP push:
  - `modules/voics-callkit` (a small local Expo module, Swift) owns `CXProvider`, `CXCallController` and the `PKPushRegistry`. The registry is created by an app delegate subscriber at launch, so a push that wakes a closed app is reported to CallKit natively before JavaScript exists, as Apple requires (every VoIP push must call `reportNewIncomingCall` before its completion handler, or iOS stops delivering VoIP pushes). A push that cannot be used, or a call that is already shown, is still reported and ended at once. A call nobody answers ends by itself after the ring time (30 s).
  - Why a local module and not react-native-callkeep or react-native-voip-push-notification: those need JavaScript running (or app delegate patches) to meet the report-first rule, and neither has a maintained release for React Native 0.88 and the new architecture. The module is about 400 lines of Swift and has no dependency beyond Apple frameworks.
  - JavaScript side (`src/voice/callkit`): `nativeCallKit.ts` is the only loader (iOS native builds only), `CallKitController` keeps CallKit and the app in step (rings reported while the app is open, calls the person starts or joins shown as outgoing, answer, decline, hang up and mute from the system UI, mute mirrored back, a ring that vanished ended once the gateway has settled), `CallKitHost` wires it to the stores. Answering on the lock screen of a closed app waits for the session and the gateway (up to 15 s), then opens the call screen, which joins. The system hands the audio session over (`RTCAudioSession.audioSessionDidActivate` of the LiveKit WebRTC package). The app's own ring card stays as the fallback in Expo Go and when the system refuses the call (Do Not Disturb).
  - The PushKit token is registered through `POST /users/@me/devices/voip` on every start and when the system rotates it. It works with notifications switched off. Logout removes it with the notification token.
  - Server side: when a DM call starts the gateway already posts the call system message; the notifier (messages repo) turns it into a VoIP push to every PushKit token of the other members who are not in the call and have not muted the conversation. The payload never carries message text; the caller's name is in it only for a `standard` conversation, and an encrypted conversation rings as an unnamed call (the app does the same for calls it reports itself). Calls rung later with Add to call reach open apps only. Details in docs `handbook/13-mobile-client.md`.
  - Apple: `UIBackgroundModes` gains `voip` (`app.config.ts`). No App ID capability changes (Push Notifications is already there; PushKit and CallKit have no entitlement), and the APNs key that sends alert pushes sends VoIP pushes to `<bundle id>.voip`. A new native build is needed (new module, new background mode).
- Android push and calls (FCM, development, preview and store builds). Not run on a phone yet; the JavaScript is unit-tested and the build compiles on EAS, nothing more.
  - Firebase: project `voics-cf336`, Android app `nl.voics.app`. `app.config.ts` sets `android.googleServicesFile` from `process.env.GOOGLE_SERVICES_JSON`, which is an EAS **file** environment variable (`GOOGLE_SERVICES_JSON`, sensitive, in `production`, `preview` and `development`; created with `eas env:create --type file --value <path>`); the file is not in git (`.gitignore` lists `google-services.json`). Without the variable (Expo Go, a local run) the config is left out, the build still compiles and push stays off (`getDevicePushTokenAsync` fails and `deviceToken()` is null). The `expo-notifications` plugin sets `messages` as the default channel of FCM notification messages.
  - Push: `nativePush.ts` now loads expo-notifications on Android too. It creates the channels `messages` (default importance) and `calls` (high) when the controller starts listening and again before the permission prompt (Android 13 shows the POST_NOTIFICATIONS prompt only once a channel exists), then the flow is the iOS one: explanation first, one system prompt, `denied` is final and the Notifications page opens the Android settings. The token is the FCM registration token and is registered as `POST /users/@me/devices/push` with `platform: "fcm"` (the value the contract already has; `environment` is always `production`, Android has no sandbox) and the same `previews` and `only_mentions`. Tapping a notification opens the chat (`pushTargetOf` reads `channel_id`, `guild_id`, `message_id` from the data). Android shows no app-icon badge count from `setBadgeCountAsync` on most launchers; the call is harmless.
  - Calls: `modules/voics-callkit/android` (Kotlin, Expo Modules API, `platforms` now `["apple", "android"]`) exposes the same functions and the `onCallEvent` stream as the iOS module, so `src/voice/callkit` is shared. `CallCoordinator` registers a self-managed `PhoneAccount` and one Telecom `Connection` per call (`MANAGE_OWN_CALLS`), and shows the incoming call as a `calls` channel notification (ringtone, vibration, `CallStyle` with Answer and Decline on Android 12+, a full-screen intent that opens `IncomingCallActivity`, a small native call screen that shows over the lock screen without the app itself doing so). Answer opens the app and emits `answer`; Decline is a broadcast and emits `end/decline`; the ring ends by itself after `ring_seconds` (default 30, 5 to 60). An answered or started call runs a foreground service (types `phoneCall` and `microphone`, with a Hang up action) so the microphone survives the background. If Telecom refuses (another call, no telecom feature), the notification still rings.
  - Closed app: `VoicsMessagingService` extends expo-notifications' `ExpoFirebaseMessagingService` and replaces it in the manifest (priority 0 against its -1, and a `tools:node="remove"` of the original). A data-only, high-priority FCM message `{"type":"call","channel_id":"...","caller_name":"...","private":"true|false","ring_seconds":"30"}` (all values strings, the same keys as the iOS VoIP payload) rings in the process the push started, before React Native exists. `{"type":"call_end","channel_id":"..."}` stops a ring the server ended. Every other message is passed to expo-notifications. Events wait in a native queue until JavaScript listens, as on iOS. There is no PushKit token on Android: `voipToken()` is null and the call push goes to the FCM token registered as the push token, so calls need the notification permission (Android 13+ hides the ring without it).
  - Manifest: the permissions (`MANAGE_OWN_CALLS`, `USE_FULL_SCREEN_INTENT`, `FOREGROUND_SERVICE`, `FOREGROUND_SERVICE_PHONE_CALL`, `FOREGROUND_SERVICE_MICROPHONE`, `POST_NOTIFICATIONS`, `VIBRATE`, `WAKE_LOCK`) and the components are in the module's own `AndroidManifest.xml`, which autolinking merges into the app; no config plugin is needed. `USE_FULL_SCREEN_INTENT` is granted automatically only to calling apps on Android 14+ (Play Console declaration); without it the ring is a heads-up notification.
  - Release builds: R8 (EAS `preview` and `production`) failed with "Missing class livekit.org.jni_zero.JniZeroJni" from the LiveKit WebRTC package, so no Android release build of this app worked. `plugins/withAndroidProguard.js` (listed in `app.config.ts`) appends `-dontwarn livekit.org.jni_zero.**` to the generated `proguard-rules.pro`.
  - Server side (messages#75, docs `runbooks/push-notifications.md`): message pushes are FCM notification messages (`title`, `body?`) with data `{type: "message", channel_id, message_id, guild_id?}`, channel `messages` and the channel id as tag. Call rings are data-only, high priority, ttl 30 s, with data `type=call`, `channel_id`, `call_message_id`, `call_id`, `caller_id`, `private`, `ring_seconds=30` and `caller_name` only for standard conversations (all strings); the Android service reads `channel_id`, `caller_name`, `private` and `ring_seconds` and ignores the rest. `call_end` (stop a ring) is supported by the app but not sent by the notifier yet. The token is registered with `platform: "fcm"` (`environment` is ignored for it) on every start and on token refresh, and deleted on logout like the iOS one.
  - The native iOS app and ReplayKit extension compile in the macOS workflow. Device push, CallKit delivery and physical-iPhone capture still require signed-device acceptance.
- iOS screen sharing (client#337): Share screen explains that the call can see notifications and other apps, then opens Apple's Start Broadcast sheet. Cancellation never publishes a track. The app's Stop sharing screen control, Control Center stop, leaving and a failed call all release capture. Going to the background stops the camera while the screen broadcast continues. Only video is shared; call audio keeps the existing microphone mute setting. Android publishing is not enabled by this change; both platforms can receive a shared screen through Watch.

The ReplayKit extension is generated by `plugins/withIosScreenShare.js`: target `VoicsBroadcast`, bundle ID `nl.voics.app.broadcast`, shared app group `group.nl.voics.app`. The plugin also declares the extension to EAS for signing. `modules/voics-screen-share` owns the native consent/lifecycle bridge; `plugins/broadcast` contains the extension and a bounded video uploader compatible with LiveKit WebRTC's `rtc_SSFD` socket. Screen content is sent in memory over that local socket, then through `VoiceSession.setScreenTrack` and the same encrypted sender gate as the camera. No separate media protocol or server change is required. The extension needs its own provisioning profile and the same App Group entitlement as the host app; generate a fresh native build after this change, since an OTA bundle cannot add it.

Camera capture now rejects starts without a connected call and discards permission results arriving after Leave. Native WebRTC may report no outgoing SSRC immediately after a track is attached; the shared session retries until the stream can be announced and cancels that work on stop/disconnect.

Desktop and mobile use VP8 by default, because the SFU forwards encoded video without transcoding between codecs. An actual Android-emulator/Windows-Electron call verified video reception in both directions, including decoded-frame counters. This is standard-call evidence, not physical-iPhone or encrypted-call acceptance. Camera switching reopens the requested capture through the existing protected sender; it does not use the native deprecated `_switchCamera`. Preview mirroring follows the captured track's actual facing, and a device with only one camera explains that the other camera is unavailable. The tested emulator exposes only one back camera, so physical front/back switching remains a device check.

The SFU does not forward the RTP camera-orientation extension. Its SDP answer therefore does not acknowledge that extension, so native WebRTC rotates the encoded pixels instead. Root QA verified upright 720 × 1280 portrait video and increasing decoded frames in the actual Electron receiver.

The local microphone and camera sections are answered `recvonly`: the SFU receives those tracks, while each remote publisher has a separate `sendonly` section with an explicit MSID. Advertising anonymous incoming tracks on the local sections created WebRTC's fallback stream and reproduced an Android `OnRemoveStream` abort after the last peer left and rejoined. After correcting the direction, root repeated two desktop peer departures/rejoins in the same native Android call with camera video in both directions; 17 heartbeats remained acknowledged (maximum interval 14.06 seconds, maximum acknowledgement delay 162 ms). Sixty-nine shared SDP/voice regressions, core typecheck and changed-file lint passed. These checks used the QA APK with production JavaScript (`expo start --no-dev --minify`); the development bundle's render overhead had caused separate heartbeat stalls. Physical-iPhone and encrypted-call acceptance remain separate checks, and this Android crash does not establish the cause of the historical iPhone crash.

Native validation: `mobile-ios-native.yml` generates the iOS project twice (checking idempotency with `node scripts/verify-ios-broadcast.mjs`), compiles the ReplayKit target, and builds the app and consent module for the ARM64 iOS simulator. The latter downloads the existing `voics-crypto-ios` artifact with the workflow token. `scripts/ios-simulator-smoke.mjs` then boots an existing CI iPhone simulator, installs that app and opens its local Metro bundle. The pinned Maestro flow in `e2e/ios-startup.yml` checks native startup and navigation between sign-in, registration and password-reset forms without submitting an account request. The `ios-simulator-smoke` artifact contains screenshots, device details and Metro/driver logs. This checks compilation and startup; it does not establish ReplayKit capture on an iPhone. On a signed physical iPhone, test camera permission denial/grant, front/back video, late permission after Leave, screen-share Cancel/Start, switching to another app, portrait/landscape, stop in Control Center, reconnect, and leave. Run each with a desktop/iPhone receiver in both standard and encrypted calls and check that the receiver sees motion, the encryption badge only appears after keys are active, and no camera/share indicator remains after stopping. The desktop-to-iPhone native crash still needs separate desktop diagnostics; these fixes do not establish its cause.

How it is built: `@discordy/core` holds the voice session (`application/voice/voiceSession.ts`), the call controller (`voiceCallController.ts`), the media ports (`ports/media.ts`, `ports/voice.ts`) and `TurnCredentials`; the desktop extends the controller with camera, screen share and devices. Mobile supplies `createPeerConnection`, the microphone (`mobileMic`), the mixer (`mobileMixer`) and the audio route. The node never sends SDP, so the session builds the answer itself from the local offer; libwebrtc on iOS must produce an offer the parser accepts (to be checked on a device).

**Ephemeral and peer-to-peer chats (client#275, native build only).** In a development or preview build that contains the `VoicsCrypto` module, Ephemeral and P2P channels and DMs open as normal chats: they read from the encrypted store on the phone (`MessageSender.loadHistory`, never the server, never the plain message cache), send text through core `PrivateMessaging` (a failed send stays as a failed message with Retry), and show the same indicators as desktop: the delivery-mode badge under the header (`ModeBadge`: Standard, Ephemeral E2EE, Peer-to-peer), and above the composer the honest link state (`PeerStatusBar`: connecting, direct link open and verified, peer offline, identity unverified with sending blocked, encryption unavailable) with the safety number sheet. Expo Go has neither the crypto module nor react-native-webrtc, so there the runtime has no `privacy` engine and the "not in this test version" notices stay. Not on mobile yet: attachments in private chats (the file cipher uses WebCrypto, which Hermes lacks; the attach button is hidden there), editing, deleting, pinning and forwarding private messages (as desktop), E2EE calls. How it is built: `src/privacy/cryptoBridge.ts` adapts the Expo module `modules/voics-crypto` (Swift over the Rust core through uniffi; the store key lives in the iOS Keychain and never reaches JavaScript), `reactNativePeerConnection.ts` is the typed seam from react-native-webrtc to `PeerConnectionLike`, `nativePrivacy.ts` is the only place that loads either (lazily, in a native build only). The XCFramework is built by the manual `crypto-ios` GitHub Actions workflow on a macOS runner and fetched into the module by `scripts/fetch-crypto-framework.mjs`, which runs as the EAS hook `eas-build-pre-install` (it needs the EAS secret `VOICS_CRYPTO_GITHUB_TOKEN`) or by hand before `expo run:ios`. Core also gained a pure UTF-8 codec and SHA-256 fallback because Hermes guarantees neither TextDecoder nor `crypto.subtle`. Not yet run on a device: see the PR description.

**Push notifications (messages#56, api#93, native build only).** `expo-notifications` (the version `npx expo install` picks, ~58.1.8) is loaded only by `src/notifications/push/nativePush.ts`, lazily, in an iOS or Android build where `isNativeBuild` is true (Android: see Android push and calls above); in Expo Go `loadNativePush()` is null and every push call does nothing, so the Notifications page says "Not available in Expo Go" and the app starts as before. `PushController` (everything outside it is injected, so it is unit-tested) listens from launch, so a tap that opened the app is kept until sign-in, then: with permission it registers the APNs device token through `POST /users/@me/devices/push` on every start (`environment`: `sandbox` for a development build, `production` for preview and store builds, from `extra.pushEnvironment` in `app.config.ts`; `previews` and `only_mentions` from the Notifications page), and registers again when iOS rotates the token or a preference changes. The permission is never asked at launch: the first time a chat is open the app explains what it is for ("Turn on notifications?") and only then shows the iOS prompt; "Not now" or a refusal is final, and the Notifications page offers Turn on or Open Settings. Logout removes the token first (`SessionManager` runs `beforeLogout`, then the server logout also drops it). Tapping a notification opens its chat and scrolls to the message (`openMessage`). While the app is open the system banner is suppressed when the gateway is live (the in-app banner covers it) or the chat is on screen, and shown only when the gateway is down, so a message is never shown twice or lost. The icon badge follows the unread mentions of the inbox while the app runs and is cleared at sign-out; the notifier does not send a badge count yet. The `expo-notifications` config plugin adds the `aps-environment` entitlement (`development` unless `EAS_BUILD_PROFILE` is `preview` or `production`). Push needs the Apple key in OpenBao (docs `runbooks/push-notifications.md`), a build signed with the Push Notifications capability, and a real iPhone: nothing here has been delivered to a device.

What each device-only risk needs: see the PR description of client#275 (microphone and audio session, `media-source` level stats, simulated SDP, react-native-webrtc under the new architecture interop layer).

## Motion and design (client#305)

**Attachment metadata.** Long-press your sent message in a Standard chat and choose **Edit
Attachments** to change descriptions and spoiler settings without uploading again. Save waits for
the service, failed saves keep the draft, and Cancel discards it. File/audio spoilers require a
reveal, and the image viewer excludes other concealed attachments. This requires messages#79;
see [the metadata guide](../../docs/attachment-metadata.md) for the contract, regression commands
and remaining native device checks. The editor is covered by React Native component tests, not
by a device/keyboard verification claim.

Native libraries (a development build is needed for a new build; Expo Go bundles all four at these versions): `react-native-reanimated` 4.7.1, `react-native-worklets` 0.13.0, `react-native-gesture-handler` 3.3.0 and `react-native-keyboard-controller` 1.22.7. `app/_layout.tsx` wraps the app in `GestureHandlerRootView` and `KeyboardProvider`; the babel preset adds the worklets plugin by itself.

- **Keyboard.** The chat list is a `KeyboardChatScrollView` (inverted, `keyboardLiftBehavior="always"`, interactive dismissal) inside a `KeyboardGestureArea`; the composer dock is a `KeyboardStickyView` floating over the list, whose measured height is the list's `extraContentPadding`. Everything follows the keyboard frame on the UI thread, the list stays pinned to the newest message, dragging the list down closes the keyboard, and the dock drops its home-indicator padding by the sticky view's `opened` offset. There is no `KeyboardAvoidingView` any more; the sign-in form uses `KeyboardAwareScrollView`.
- **Gestures.** Sheets (`BottomSheet`), swipe to reply (`SwipeToReply`) and the member-list swipe (`MembersEdgeSwipe`, a 16 pt strip on the right edge of a server chat; drag 60 pt left or flick) use gesture-handler pans and reanimated shared values, with `swipeModel`, `sheetMotion` and `edgeSwipeModel` as the pure worklet rules the tests cover. The stack's back swipe works from anywhere on the screen (`fullScreenGestureEnabled`). Reduce Motion (app or iPhone) turns every movement into an instant change.
- **Scales and primitives** (`src/theme.ts`, `src/ui/`): `type` (desktop's 11 to 30 ladder), `space` (4 to 64), `radius` (6, 10, 14, 20), `HIT` (44), `CHROME_FONT_CAP` (1.3: text in fixed-height rows and chips stops growing there, message text grows freely). `Txt` (variant, tone, weight, `chrome`, `caps`), `PressableScale` (0.97 scale, 150 ms), `Button` (44 pt, `size="large"` 48 pt), `Input` and `Field` (accent border on focus), `ListRow` (52 pt), `SectionHeader`, `EmptyState` (icon tile, headline, sentence, one action) and the `Skeleton`, `MessageSkeletons` and `RowSkeletons` loaders that replace spinners and "Loading..." lines. New screens use these instead of their own sizes.
- **Jest.** Gesture-handler is mocked as chainable no-ops in `tests/setup.ts` and reanimated runs through its Jest resolver (`jest.config.js`), so gestures are tested through their pure models, not by simulated touches.

## Presence across suspension

`runtime/foreground.ts` publishes P7 presence before `AppState` enters the background and after
READY/RESUMED. A brief `inactive` state (for example Control Centre) does not change presence.
Normal Online becomes automatic Idle; choosing Online in the status picker persists an explicit
Online choice in device storage under the authenticated account ID. Other accounts on the same
phone do not inherit it. Choosing Idle, DND or Invisible clears that explicit Online preference.
Custom statuses and their expiry still use the shared core rules.

The client sends `background: true` only while backgrounded. The gateway retains the effective
status across suspension for a bounded lease (24 hours by default), removes it on logout/revocation
or expiry, and aggregates it with the user's other devices. This cannot distinguish suspension
from an iOS force-quit. No keepalive audio, background timer or fake heartbeat is used. On cold
start the client identifies as invisible until READY loads saved account settings, preventing
an Invisible or DND account from briefly appearing Online. A live socket also receives Invisible
before local logout closes it if the logout HTTP request failed.

Regression commands: `pnpm --filter @discordy/mobile test --runInBand tests/runtime/foreground.test.ts tests/runtime/createRuntime.test.ts`.

## Run it on a phone (no Mac needed)

1. **Expo Go (fastest).** Install Expo Go from the App Store or Google Play. Put the phone and PC on the same Wi-Fi, run `pnpm dev:mobile`, and scan the QR code (iPhone: Camera app; Android: Expo Go). If the phone cannot reach the PC (firewall, guest Wi-Fi), run `pnpm --filter @discordy/mobile start -- --tunnel`. Everything uses Expo Go compatible modules (including `expo-clipboard` and `expo-image-picker`, added for invite copying and the server icon).
2. **Development build.** Needed for voice (@livekit/react-native-webrtc is native; Expo Go does not have it). `eas.json` has two profiles, `development` (dev client, internal distribution) and `preview` (internal distribution, auto-increment); both are for a pnpm monorepo and run from `apps/mobile`. Build in the cloud with EAS (`npx eas-cli build --profile development --platform ios`); an iPhone build needs an Apple Developer account and the iPhone registered (owner steps, docs#10). Android push and calls need the `GOOGLE_SERVICES_JSON` EAS file variable (see Android push and calls); an Android build is `npx eas-cli build --profile preview --platform android` (an installable APK for internal distribution) or `--profile development`, and it has not been run on a phone. The website APK: the `apk` profile (production settings, internal distribution, `buildType: apk`) builds it with `npx eas-cli build -p android --profile apk`; publish it with the `android-apk` workflow (`gh workflow run android-apk.yml -f apk_url=<EAS artifact URL> -f version=<app version>`), which puts `Voics-<version>.apk` and `Voics-latest.apk` on https://updates.voics.nl and attaches it to the GitHub Release `android-v<version>`. The signing keystore is kept by EAS (remote credentials, shared by all Android profiles); every update must be signed with it or phones refuse to install it over the old one. Then start with `pnpm --filter @discordy/mobile start:dev-client`.
3. **Simulators.** The iOS simulator needs macOS. On Windows use a real iPhone, or the Android emulator from Android Studio (press `a` in the dev server).

Full walkthrough: docs repo `runbooks/run-the-mobile-app.md`.

### Isolated Android emulator QA

Set `VOICS_MOBILE_QA=1` before both native generation and Metro startup. This builds
`Voics QA` (`nl.voics.app.qa`, scheme `voics-qa`) alongside the installed release.
The defaults target the host through Android's emulator alias:
`http://10.0.2.2:28100`, `ws://10.0.2.2:28100/gateway`, and
`http://10.0.2.2:28100/cdn`. Run an isolated local gitops Compose stack on port 28100
and seed local test accounts before signing in.

From `apps/mobile`, run `pnpm exec expo prebuild --platform android --no-install`,
then `pnpm exec expo run:android --device` and select the existing emulator.
For an already installed development build, run `pnpm start:dev-client` with the
same environment. `VOICS_QA_API_URL`, `VOICS_QA_GATEWAY_URL`, and `VOICS_QA_CDN_URL`
override the three endpoints when the local stack uses different ports. The API
setting is the origin; the shared HTTP client appends `/api/v1` itself.
QA alone permits Android cleartext HTTP and omits production Firebase config;
push delivery requires a separately configured native build and cannot be proven
by this QA build. Production, preview and published APK EAS profiles reject the
QA opt-in. With the variable absent, the shipped identity and URLs are unchanged.

On Windows, a deep worktree can exceed the old Ninja path limit. Install SDK CMake
3.31.6 and build from `android` with `./gradlew.bat :app:assembleDebug
'-PreactNativeArchitectures=x86_64' '-Pandroid.cmakeVersion=3.31.6'` for an x86_64
emulator. Quote the Gradle properties in PowerShell. Windows long-path support
must already be enabled; see the [Expo Windows build guide](https://docs.expo.dev/troubleshooting/windows-long-paths/).
